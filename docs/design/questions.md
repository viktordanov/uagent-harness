# The agent's questions (`request_user_input`)

Status: built (ledger item 118). The package READMEs hold the current contract; this record keeps the research and the decisions.

Ledger item 118, from [issue #4](https://github.com/viktordanov/uah/issues/4): a user wants the agent to end its work with a few blocking questions, each with plausible ways to resolve a problem, and to answer them by picking an option. Until now uah had no question tool: the system prompt told the model to ask in its final message (hunk 4 of the [system prompt](system-prompt.md)). The owner rejected Codex's asynchronous question tool, which asks while the agent keeps working and proceeds after a timeout. A blocking question that stops the agent until the user answers fits.

## What Codex does

Checked against Codex `main` at b741e48 (2026-10-03). Paths are under `codex-rs/`.

- **Two tools.** `request_user_input` waits for the answer; `request_user_input_async` (`core/src/tools/handlers/request_user_input_async.rs`) does not, and its prompt text (the 60-second wait, "Elapsed time is not an answer") is what uah's hunk 4 replaced. This record is about the first.
- **The name and schema** (`core/src/tools/handlers/request_user_input_spec.rs`): a function tool `request_user_input`, not strict, with one required argument, `questions`: "Questions to show the user. Prefer 1 and do not exceed 3". Each question has `id` ("Stable identifier for mapping answers (snake_case)."), `header` ("Short header label shown in the UI (12 or fewer chars)."), `question` ("Single-sentence prompt shown to the user."), and `options`: "Provide 2-3 mutually exclusive choices. Put the recommended option first and suffix its label with "(Recommended)". Do not include an "Other" option in this list; the client will add a free-form "Other" option automatically." An option is `label` ("User-facing label (1-5 words).") and `description` ("One short sentence explaining impact/tradeoff if selected."). Every object has `additionalProperties: false`. There is no multi-select. The description: "Request user input for one to three short questions and wait for the response. This tool is only available in Plan mode."
- **Validation** (`normalize_request_user_input_tool_args`): every question needs non-empty options ("request_user_input requires non-empty options for every question"), and the handler marks each question `isOther`, so the client adds the free-form choice. The count limits are only in the text.
- **Where it is offered.** `ModeKind::allows_request_user_input` is true for Plan mode only (`protocol/src/config_types.rs:700`); the feature `default_mode_request_user_input` (under development, off) adds Default mode (`tools/src/tool_config.rs:17`). The tool is registered unless `[tools] experimental_request_user_input` turns it off; in another mode a call fails with "request_user_input is unavailable in Default mode". The collaboration-mode templates tell the model when to use it: Plan mode "strongly prefer using the `request_user_input` tool to ask any questions", Default mode "strongly prefer making reasonable assumptions", "Never use the `request_user_input` tool for permission requests", and "If `request_user_input` returns no answers, continue with best judgment" (`collaboration-mode-templates/templates/plan.md`, `default.md`).
- **Subagents.** The handler refuses every thread but the root: "request_user_input can only be used by the root thread" (`request_user_input.rs:67`).
- **The answer.** The handler waits for the client's response with no time limit (`is_blocking` in Plan mode, no `auto_resolution_ms`), and returns it as the call's output: `{"answers":{"<id>":{"answers":["<label>","user_note: <text>"]}}}` (`protocol/src/request_user_input.rs`, `RequestUserInputResponse`). An interrupt ends the wait with "request_user_input was cancelled before receiving a response". The turn then goes on.
- **The TUI** (`tui/src/bottom_pane/request_user_input/mod.rs`, its snapshots): an overlay in the bottom pane. `Question 1/2 (2 unanswered)`, the question, the options numbered with their descriptions and the selected one marked `›`, and an added `None of the above` ("Optionally, add details in notes (tab)"). ↑↓ or a number choose; tab opens notes for the selected option, and typing on the options jumps into them; enter answers and goes to the next question, the last one submits; ←/→ go between questions; submitting with unanswered questions asks first; esc interrupts the turn. The answer is the option's label, then `user_note: <notes>`. After the answer, the transcript shows the questions and answers.
- **`codex exec`** rejects the request: "request_user_input is not supported in exec mode for thread `…`" (`exec/src/lib.rs:2110`). Exec runs in Default mode, where the tool fails anyway.

## What Claude Code does

From the Claude Code documentation ([tools reference, "AskUserQuestion tool behavior"](https://code.claude.com/docs/en/tools-reference#askuserquestion-tool-behavior), 2026-10-03) and the tool's definition, as the reference for the picker.

- **AskUserQuestion** asks 1 to 4 multiple-choice questions, each with a `header` (12 characters at most), the `question`, 2 to 4 `options` (a label and a description), and `multiSelect`. The user picks an option, or types their own text in the `Other` row or the notes field, and Claude Code relays a typed answer "with neutral wording so Claude follows what you wrote".
- **No timeout by default.** "Questions stay open until you answer them." The `askUserQuestionTimeout` setting (60 s, 5 min, or 10 min) closes an unanswered question and tells Claude the user may be away; permission prompts never resolve on idle.
- **The picker** shows the headers as tabs, the options numbered with their descriptions, and the Other row; the arrows or a number choose, and enter answers.

## The design

1. **The tool** is Codex's: the name, the description's first sentence, and the schema, word for word, so a model trained on Codex calls it as it does there. "This tool is only available in Plan mode." is left out, since uah has no modes. The engine checks what Codex checks, plus a unique `id` per question and at least one question, which the answers need.
2. **Who gets it.** The engine offers it (`embedded.Config.AskUser`) when a user drives the sessions and the setting allows it: the TUI sets `app.Inputs.Interactive`, and `[tools.experimental_request_user_input] enabled = false`, Codex's key, or `UAH_REQUEST_USER_INPUT=off` turns it off (below). The main agent asks through `engine.Options.AskUser`, which an interactive session fills. A child started with `fork_context` is offered it too and refused with Codex's root-only message, so its tools stay its parent's and its first request keeps the parent's prompt cache, as the spawn tools stay for a fork at the depth limit ([subagents](subagents.md)). A plain child is not offered it; it asks its parent in its final answer. A scope can leave it out, as `/review`'s reviewer does.
3. **Blocking.** The wait is the call's decision, as an approval's is (`gatedTranslator`): the prefetcher starts it when the response is stored, and the coordinator's loop waits in `Translate` until the user answers. So neither the 10-minute heartbeat nor the 5-minute wake valve reaches the model meanwhile, and there is no time limit. An interrupt ends the wait through the run's approval context, and the call fails with Codex's cancelled message.
4. **The answer** returns as the call's result in Codex's encoding. An answered call runs as a remote job (`uah.request_user_input`) that completes at once: the runner has no other way to give a successful result, and the job's plan keeps the questions and the answers in the session file. The observer emits `engine.QuestionsAnswered` from that item, and `session.Load` adds it to a loaded transcript, as for patches.
5. **The session** relays the questions like an approval: `QuestionsAsked` with an ID, `Session.AnswerQuestions`, and `QuestionsAnswered`, canceled by an interrupt, the run's end, or `Close`.
6. **The TUI** draws a panel above the composer, where the approval goes, and the approval shares its design (version 1.8.2): a frame in the accent across the width with the title in its top edge and the keys in its bottom edge, the body on the band's tint, and the choices as rows of key, label, and help, so both stand apart from the transcript and read as one family. The question's panel has `? <header>` (and `· 1 of 2`) in the frame, the headers as tabs when there are several (an answered one with ✓), the question in bold, the options numbered with their descriptions dim and the chosen one in the accent band, `None of the above` ("Type your answer below."), and the keys. ↑↓ choose; a number on an empty composer picks and answers; the composer holds the answer's note, and typing on a row the user did not choose moves to `None of the above`, so a typed answer stands on its own (Claude Code's "Other"); enter answers and shows the next unanswered question, or sends every answer; tab and shift+tab go between the questions, each keeping its own note; esc, or ctrl+c on an empty composer, interrupts the run, as Codex's esc does, and the draft stays, so the user can write the message they want instead. The status line says `Waiting for your answer`, the title `answer?`. The call's line reads `ASK` with its question (or the headers of several), and the answers go under it, one per question (`Migration: Rename in place`).
7. **Headless runs** (`uah exec`) do not get the tool: no one could answer. The model asks in its final message, which `uah exec` prints, and a script answers with `uah exec resume`. Codex's exec rejects the call; leaving the tool out saves the model the failed call and the tokens of its definition.
8. **The prompt.** Hunk 4 keeps "ask in the `final` channel" and adds when to use the tool (unless the setting turns the tool off; then item 63's text stands): "When the `request_user_input` tool is available and the answer is a choice between a few plausible options, ask with the tool instead", at the end of the work that does not depend on the answer or when the agent cannot proceed, never for permission, never for files. With the tool on, the prompt is the same whether a run offers it or not, so the system message, and with it the prompt cache, does not depend on the client.

## Decisions

- **Codex's tool, not a new one.** The name and schema match Codex, the parity rule; the limits (1 to 3 questions, 2 to 3 options) stay in the text, and uah draws any number.
- **The answer is the tool's result**, as in Codex, not the next user message. The run stays live while it waits, as for an approval.
- **A setting to turn it off** (version 1.8.2, for the owner's web terminal, which cannot show the picker): `[tools.experimental_request_user_input] enabled`, Codex's own key and shape, true by default, merged like every key, so a `config.d` layer, the file `UAH_EXTRA_CONFIG` names, or a trusted project file can set it, and `UAH_REQUEST_USER_INPUT` (`on` or `off`) wins over the files. Off, the tool is not offered, and the default system prompt (or a `model_instructions_file` with the same text) gets item 63's hunk-4 text back word for word (`instructions.WithoutQuestionTool`), so the model asks in its final message. Otherwise the tool follows who can answer: the TUI offers it, `uah exec` does not.
- **No multi-select**, as in Codex.
- **esc interrupts.** Codex's esc interrupts the turn; uah's interrupt keeps the draft, so "dismiss and type normally" is the same key. A dismissal that answered "no answer" and let the agent go on would race with the user's typing.
- **Approvals are unaffected.** A question is not an approval: yolo mode, auto mode, and the auto-reviewer do not answer it, and PermissionRequest hooks do not see it. PreToolUse hooks match it like any tool. The auto-reviewer's transcript keeps each answer with the user's messages, trusted (the question, the chosen option's description, and the answer), as Codex keeps a `VerifiedAnswer` for its guardian, so "drop the old table" chosen in the picker counts as the user's word.
- **Resume, fork, and rewind.** A run that stops ends the wait, so the call has its cancelled result in the session file, and a resumed session goes on from it: the next message reaches the model after it. A run that crashed mid-question leaves the call without a status; the coordinator translates such a call again on the next run (the [engine](../../internal/engine/README.md#approvals-for-parallel-calls)), so the question shows again. A fork copies answered calls as history. A rewind needs an idle session, which a pending question never is.
